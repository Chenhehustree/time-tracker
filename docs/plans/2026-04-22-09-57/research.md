## 1. Research Summary

本项目是一个单文件计时工具（`time-tracker.html`，3655 行），采用纯原生 Vanilla JS 构建，无前端框架、无构建工具，数据通过浏览器 `localStorage` 按日期隔离存储。当前 UI 为 Modern Dashboard 风格，包含侧边栏导航和 4 个视图（Dashboard、今日任务、历史记录、设置）。核心问题集中在三点：**completed 任务无法重新计时**、**任务卡片信息拥挤**、以及**单文件架构导致维护困难**。

BlueprintUI 是 Palantir 开发的 React 组件库，面向桌面端企业级应用，提供丰富的 CSS 工具类（类似 Tailwind 但更具语义化）、暗黑主题支持，以及 Button、Card、Dialog、Tree 等关键组件。但在纯 HTML/JS 环境中只能使用其 CSS 样式，交互组件（Dialog、Tree 等）需要 React 运行时。

## 2. Key Findings

### 2.1 Completed 任务无法重新计时

- **根因**：`buildTaskCardHTML()` 对 `completed` 状态未渲染任何操作按钮；`canStart()` 函数对 `completed` 返回 `false`；设计文档明确将 `completed` 定义为终态
- **影响**：用户完成一个任务后无法继续或追加记录，只能创建同名新任务，导致数据分散

### 2.2 信息拥挤

- 单卡片承载：任务名、状态标签、实时计时器、累计时长、操作按钮、Toggle、多个时间段详情
- 24小时时间轴在约 600-700px 宽度内展示，短时间段（<30 分钟）几乎不可见
- 任务卡片与时间段列表背景色相近，视觉层次模糊
- Dashboard 纵向堆叠，超过 5 个任务需大量滚动

### 2.3 架构债务

- 单文件 3655 行，含约 1500 行自测代码，CSS 无模块化
- 大量 V1 遗留测试失效
- 缺少任务删除功能

### 2.4 BlueprintUI 适用性

- **优势**：语义化 CSS 工具类、原生暗黑主题、企业级视觉风格与当前 Dashboard 定位契合
- **限制**：无原生 Timeline 组件；纯 HTML/JS 无法使用交互组件；全量引入约 200KB+ gzip；桌面优先，移动端体验一般

## 3. Trade-offs

### 3.1 技术路线：React + Blueprint 完整重构 vs 纯 HTML/JS 引入 Blueprint CSS

| 维度 | React + Blueprint | 纯 HTML/JS + Blueprint CSS |
|------|-------------------|---------------------------|
| 项目结构 | 重大改变，需构建工具链 | 保持单文件，低风险 |
| 可用组件 | 全部（Dialog, Tree, Table 等） | 仅 CSS 样式和静态结构 |
| 时间线展示 | 可用 Tree/Table 实现层级展示 | 需自行构建，无法使用 Tree 组件 |
| 维护成本 | 长期更低（组件化） | 短期更低，长期技术债务累积 |
| 决策依赖 | 用户是否接受引入构建工具 | — |

### 3.2 Completed 任务重新计时方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 允许 completed 直接恢复为 running | 简单直接 | 破坏终态语义，状态机复杂度增加 |
| B | Completed 任务只能"新建时间段" | 保持终态，数据模型清晰 | UI 需新增"追加记录"入口 |
| C | "重启任务"按钮，实质创建新任务 | 完全不改动状态机 | 数据分散，历史记录碎片化 |

**倾向**：方案 B，兼顾状态机简洁性和用户实际需求。

### 3.3 时间段列表展示方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 卡片内嵌时间轴，优化宽度 | 保持现有交互习惯 | 空间有限，<30 分钟段仍难展示 |
| B | 时间段独立到侧边面板/弹窗 | 释放卡片空间，展示更充分 | 增加交互层级，需额外点击 |
| C | Blueprint Tree 组件层级展示 | 结构清晰，可折叠 | 需要 React 环境 |

**倾向**：若选纯 HTML/JS 路线，采用方案 A 优化或方案 B；若引入 React，优先方案 C。

## 4. Open Questions for Design

1. **技术路线决策**：用户是否接受引入 React 构建工具链，还是坚持纯 HTML/JS 方案？这决定了 BlueprintUI 的使用深度和时间段展示方案的选择范围。

2. **"重新计时"语义**：用户期望的"重新计时"是恢复 completed 任务继续追加记录（方案 B），还是创建同名新任务（方案 C）？这影响状态机和数据模型的设计。

3. **时间段展示位置**：理想情况下时间段列表是保持卡片内嵌（减少点击），还是独立到面板/弹窗（释放空间）？若接受 React，是否使用 Blueprint Tree 组件？

4. **时间轴去留**：24小时拖拽时间轴是核心交互还是视觉负担？是否改用更紧凑的时间编辑方式（如起止时间输入框）？

## 5. Recommendation

基于当前纯 HTML/JS 的单文件架构，**建议优先采用低风险路线**：

1. **引入 Blueprint CSS**：通过 CDN 引入 `@blueprintjs/core` 的 CSS 文件，使用其工具类、色彩和排版系统重绘 UI，获得一致的视觉风格，无需构建工具
2. **状态机优化**：采用方案 B（completed 任务允许"新建时间段"），在 `canStart()` 中增加对 completed 状态的例外处理，UI 上为 completed 任务渲染"追加记录"按钮
3. **卡片信息分层**：将时间段列表默认折叠，仅展示累计时长和最近一个时间段，点击展开后全屏覆盖层或侧边面板展示完整列表，缓解信息拥挤
4. **任务删除功能**：补全缺失的任务删除能力，防止数据无限累积

若用户明确接受引入 React，则可升级到完整 Blueprint 组件方案，使用 Tree/Table 重构时间段展示，获得更好的可维护性和扩展性。
