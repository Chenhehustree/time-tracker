## 问题 1：技术路线选择

**我提出的问题**：
关于 BlueprintUI 的引入方式，当前项目是纯 HTML 单文件（3655 行），无构建工具。我分析了三种方案：

**方案 A（推荐）：纯 HTML/JS + Blueprint CSS**
- 通过 CDN 引入 Blueprint 的 CSS 文件，使用其工具类、色彩和排版系统重绘 UI
- 优点：保持现有单文件架构，无需构建工具，双击即用，风险最低
- 缺点：只能使用 Blueprint 的视觉样式，无法使用 Dialog、Tree、Table 等交互组件

**方案 B：React + Blueprint 完整重构**
- 引入 React 和 Blueprint 组件库，完整使用所有组件
- 优点：可使用 Tree/Table 等高级组件重构时间段展示，长期可维护性更好
- 缺点：项目结构重大改变，需要构建工具链（Webpack/Vite），失去"双击即用"的便利性

**方案 C：混合方案**
- 先引入 Blueprint CSS 做视觉重绘，后续再考虑是否升级到 React
- 优点：渐进式改造，风险可控
- 缺点：两次改造，总工作量可能更大

> **用户回答**：方案 A：纯 HTML/JS + Blueprint CSS（推荐）

## 问题 2：重新计时行为

**我提出的问题**：
当前设计中，completed（已结束）的任务是终态，没有任何操作按钮。我分析了三种可能的实现方式：

**方案 A：直接恢复计时**
- completed 任务可以点击"继续计时"，状态变回 running，在当前任务下追加新的时间段
- 优点：操作最直接，用户感知上就是"同一个任务继续"
- 缺点：completed 不再是终态，状态机变复杂，"已完成"的语义被削弱

**方案 B（推荐）：追加记录**
- completed 任务显示"追加记录"按钮，点击后在该任务下新增一个时间段并开始计时
- 优点：保持 completed 的终态语义，数据模型清晰，历史记录不会混乱
- 缺点：UI 上需要明确区分"继续"和"追加"

**方案 C：重启为新任务**
- completed 任务显示"重启"按钮，实质是创建一个同名的新任务，从零开始计时
- 优点：完全不影响原有已完成数据
- 缺点：历史记录分散到多个任务中，难以查看累计工时

> **用户回答**：方案 B：追加记录（推荐）

## 问题 3：时间段展示方式

**我提出的问题**：
当前每个任务卡片内嵌展示所有时间段，包含 24小时拖拽时间轴、起止时间、时长、删除按钮等。当时间段较多或较短时，进度条几乎不可见，所有信息挤在一起。

**方案 A（推荐）：卡片内优化 + 独立面板**
- 任务卡片默认只展示任务名、累计时长和最近一个时间段
- 点击"展开详情"后，在卡片下方或侧边滑出独立面板展示完整时间段列表
- 独立面板内时间轴宽度充足（可达 800px+），短时间段也能看清
- 优点：减少默认视图的信息量，展开后空间充足，交互清晰
- 缺点：需要一次点击才能看到完整列表

**方案 B：弹窗/抽屉展示**
- 点击任务卡片的"查看记录"按钮，弹出 Dialog 或右侧抽屉展示所有时间段
- 优点：完全释放卡片空间，弹窗内可自由布局
- 缺点：增加交互层级，频繁查看时需要多次点击

**方案 C：保持内嵌，优化布局**
- 去掉 24小时时间轴，改用更紧凑的文本列表（起止时间 + 时长）
- 将编辑操作收到下拉菜单中
- 优点：无需额外点击，一屏可见
- 缺点：丢失了时间轴的可视化优势，编辑时间仍需额外操作

> **用户回答**：方案 A：卡片内优化 + 独立面板（推荐）

## 问题 4：时间轴设计

**我提出的问题**：
当前每个时间段都有一个 24小时制的时间轴，两端可以拖拽调整起止时间。但这也占用了大量空间，且短时间段几乎无法拖拽。

**方案 A（推荐）：保留时间轴，移至独立面板**
- 在展开后的独立面板中保留 24小时时间轴，宽度充足后可正常使用
- 任务卡片默认视图只显示文本形式的时间信息
- 优点：保留了可视化和拖拽编辑能力，空间问题在面板中解决
- 缺点：面板内仍需要一定高度

**方案 B：去掉时间轴，改用时间输入框**
- 所有时间段改用文本展示（09:00 - 11:30）
- 点击编辑时弹出时间选择器或输入框
- 优点：更紧凑，信息密度高，适合列表展示
- 缺点：失去了一目了然的时间分布可视化

**方案 C：简化时间轴**
- 时间轴不再表示 24 小时，只显示相对比例（该任务当天的占比）
- 或改为迷你进度条形式
- 优点：保留可视化但减少空间占用
- 缺点：失去了绝对时间的直观对比

> **用户回答**：方案 A：保留时间轴，移至独立面板（推荐）
